# 重复复杂算法压缩（code factoring）

## 1. 目标与边界

按 11-04 定调的三根轴：体积小 / 内存安全 / C 高度互操作，只改 mcs2 后端，
51 先行、251 押后。本项属于「体积小」轴，做法是把编译单元里反复出现的
**复杂算法**直线算术块压成一份共享子程序，调用点改成 `lcall`。

- **不新增静态槽**：共享例程复用「第一次出现该块的函数」的 vreg 基线，
  块内相对槽号经 `byteOf` 加同一基线即对上；DSEG 不涨，80 B 上限不破。
- **不碰边界 ABI**：`_名_PARM_n`、DPL/DPH/B/A 的摆放完全不动，C↔Zig 混链门禁照常。
- **ISR 不参与**：中断可能打断拥有者函数，而共享例程用的正是它的槽。
- **尺寸档零例外**：`ReleaseSafe` 的溢出/边界检查与 panic 块在提取之前生成，
  本 pass 跑在所有后端优化之后，不触碰它们。

## 3. 算法

1. **块识别**：连续直线算术 op（白名单：imm/add/sub/位运算/clr_c/addc/subb/
   mul/mul16/div_/rem_/移位/rlc/rrc/mov/dec）。带 SFR 直址、私有符号、标签、
   跳转、内存访问、调用的一律当块边界——共享例程不能依赖调用者的地址环境。
2. **「复杂算法」的硬定义**：块内至少 **2 个高成本运算**（乘/除/多字节进位链/
   移位链），且块长 ≥ 5 op。一条 `add` / `anl` / `mov` 本身 1～3 B，搬进子程序
   再用 `lcall` 调回来必然更大更慢；廉价指令只在陪伴复杂算法时一并搬走。
3. **指纹**：块内 vreg 按首次出现顺序归一化（各函数的 op 用相对槽号，
   天然同构），定长 12 B/op 编码，会话级线性查表。
4. **输入/输出**：`inputs` = 块内**首次访问是读**的槽（读-改-写槽也算输入）；
   `outputs` = 块内写过的槽 ∩ 块之后仍会被读的槽。读写集合必须「先读后写」，
   否则 `rlc a` / `subb a` 这类 dst==src 的原地指令会被误判成中间量。
5. **精确收益判据**：把块真的编译成汇编文本，按 8051 编码长度**逐条数出机器码
   字节**，与「站点搬运 ×3 B + lcall 3 B」比较；不划算就整块保持内联。
   用编译时间换尺寸精度——51 固件规模小，这个取舍划算。
6. **同函数重复整组放弃**：共享例程复用拥有者的槽，同一函数内第二个站点会
   把第一个站点的活值踩掉。只在「本函数内该指纹恰好出现 1 次」时提取。
7. **站点**：拥有者零搬运（共享例程就用它的槽），其它函数先搬输入、`lcall`、
   再搬输出。定义文本接在拥有者函数之后，`.globl _mcs_sh_N` 供同汇编单元引用。

## 4. 尺寸数据（`.ihx` 的 CSEG 数据字节）

合成用例：N 个同构 `a *% b` 导出函数，同一极简驱动。

| 调用点 N | 全部内联（关） | 共享压缩（开） | 差额 |
|---:|---:|---:|---:|
| 1 | 64 B | 68 B | +4（lcall 3 B + ret 1 B） |
| 2 | 125 B | 93 B | **−32** |
| 3 | 186 B | 118 B | **−68** |
| 4 | 247 B | 143 B | **−104** |

斜率 **61 B/点 → 25 B/点**。盈亏点在 **N=1 与 N=2 之间**：

- N=1 亏（合成用例 −4 B；完整程序口径 16 位 −8 B、32 位 −14 B，因为单站点也要付整份例程）；
- N≥2 立刻回本（N=2 省 32 B，N=4 省 104 B）。

换句话说，**单站点函数共享是净损失**。当前实现逐函数决策、看不到全单元还有没有第二个站点，
这是 §9 第一条限制的实测代价；判据只能保证「一旦有第二个站点就划算」。
站点自身的额外开销只剩一条 `lcall`（3 B）——比 SDCC 的 9 B 还低。

真实负载（整份汇编单元的 CSEG）：

| 源文件 | 关 | 开 | 共享站点 |
|---|---:|---:|---:|
| `div.zig` | 209 B | **196 B** | 0（判据拦下；−13 B 来自槽回收） |
| `mul.zig` | 125 B | **93 B** | 2 |
| `cordic_sin.zig` | 510 B | **497 B** | 0（判据拦下；−13 B 来自槽回收） |

后两者的 −13 B 不是共享压缩的功劳，是同一轮里修好的**宽局部量槽回收**
（见 §8）让 vreg 编号压回 bank0 工作寄存器区、指令变短。

**口径提醒**：`bench_compare.py` 只量「单个函数体」，共享子程序是函数外的独立
符号，不计入该函数，所以开关对照在它那里看不出差别。共享压缩的收益必须用
`.ihx` 总字节（`exp_factor.py real`）来看。早期版本没有收益判据时，
`div.zig` / `cordic_sin.zig` 反而 +3 B / +16 B，判据就是为此加的。

**更别用 HEX 文件大小判断体积**：Intel HEX 是 ASCII 文本，每行 `:LLAAAATT` +
数据 + 校验和，实测膨胀 **2.5～3.9 倍**（同一份 21 B 固件写成 `.ihx` 是 68 B）。
`bincompare.py` 把三方产物真的转成 `.bin` 再比，并给出「有效字节 / BIN 跨度 /
空洞 / 膨胀比」四个口径；它与 `fwsize.py` 的 ROM 列交叉核对完全一致
（mcs2 21/91/122/185/222/335/152、SDCC 181/229/241/318/309/395/227、
Keil 27/55/122/123/250/318/60）。三方 BIN 里的中间空洞：mcs2 / Keil 为 0，
SDCC 固定 5 B。


## 5. 与 C 编译器的口径

SDCC / Keil 在 `u16mul`、`u32div` 上的 9～15 B 是**站点跳转**到一份共享库
（`__mulint` / `?C?LNEG` 同构），不是把算法内联进每个函数；mcs2 原先是每处
展开，所以函数体大一个量级。本项正是往 C 编译器的策略靠拢。

另一方面，通用平台上「Zig 比 C 更小更快」的观察通常来自：无隐式运行时、
静态链接无 glibc 膨胀、comptime 替代模板实例化、LLVM 全程序优化。
**本项目不是那条路径**——mcs2 是自研 8051 后端，静态槽 ABI + 每处内联，
实测仍明显大于 SDCC/Keil（`u32div` 199 B 对 15 B）。差距的下一半在
**站点 ABI 搬运**（`exp_shared.py` 实测 30 B 对 SDCC 9 B）：参数先快照进
`_mcs_vN` 再逐条摆到 DPL/DPH 与 PARM 区。这一刀比推广共享库更直接。

共享调用会增加 `lcall`/`ret` 周期，是**尺寸换速度**；当前 mcs2 在除法上
周期数已高于 SDCC，压缩后会再略增。若某函数对周期敏感，应通过
`enable_factor` 或后续的函数级开关关掉它。

## 6. 验收

`python tools/mcs2/mcs2.py check` → **154 项全绿**，尺寸门禁 `_add` 7 B、
C↔Zig 混链门禁通过。新增 4 项：

- `factor_a/b/c`：三个站点各算一次，断言产物里 `lcall _mcs_sh_` ≥ 3 且
  结果正确（含 `0xFFFF *% 2` 的回绕）。
- `factor_a/b/c` 的 `no_site_shift`：断言产物里**没有** `mov _mcs_vX,_mcs_vY`
  形式的 vreg 搬运——站点槽重绑定一旦失效立刻变红。
- `factor_cheap`：加减/位运算的两个同构函数，断言**没有**共享调用，
  结果 `7 ^ 0x5A = 0x5D`。
- `safe_rec_reject` 的 `want_code2`：非尾递归的错误信息里必须出现从 AIR
  还原的真实表达式 `rec_bad((n - 1)) + 1`，防止 M1 静默退化成纯骨架。

## 7. 站点槽重绑定（本轮最大改动）

### 7.1 问题

非拥有者站点原来的形状是「私有槽 → 共享槽」逐字节搬：

```asm
mov _mcs_v9,0x82          ; 参数落私有槽（内联时也有，不算共享引入）
mov _mcs_v0,_mcs_v9       ; ← 搬到拥有者槽，4 条 = 12 B
lcall _mcs_sh_0
mov _mcs_v13,_mcs_v4      ; ← 搬回，2 条 = 6 B
mov 0x82,_mcs_v13
```

站点比内联多 21 B（18 B 搬运 + 3 B lcall），是斜率 43 B/点的主要成分。

### 7.2 判据：块专用临时量

若站点槽在**块前只被一条 `mov v, S` 触碰、块后彻底死掉**，那它的唯一用途
就是喂给共享例程——把这个定义的**目的地**直接换成拥有者槽即可，等价于
「搬家」而不是「复制」。站点连一次搬运都不用付。

输出侧同理但方向相反：块后所有使用都是纯读（`mov D,v` / `store_dir 0x82,v`）
时，把读取源直接指向拥有者槽，搬出也一并省掉。

两条判定都写在 `factor.zig` 的 `reboundDef` / `reboundOut`，用 `touches()`
做**保守**的读写扫描：凡拿不准的 op 一律按「触碰」处理，多判一次只是放弃
一次优化，不会生成错代码。

### 7.3 效果

```asm
mov _mcs_v0,0x82          ; 定义直接落在拥有者槽
mov _mcs_v1,0x83
mov _mcs_v2,_m1_PARM_2
mov _mcs_v3,_m1_PARM_3
lcall _mcs_sh_0
mov 0x82,_mcs_v4          ; 读的源直接是拥有者槽
mov 0x83,_mcs_v5
ret
```

站点额外开销 **21 B → 3 B（只有 lcall）**，斜率 **43 → 25 B/点**。

### 7.4 收益判据的重新校准

站点便宜了，原来的判据 `本体 < 站点成本 + 8` 会**过度保守**（把真正划算的
块拦在外面），而按「重绑后的乐观成本」估又会**过度乐观**（CORDIC 的
`atan2` 会因此变大）。最终口径：

```
门槛 = (入槽数 + 出槽数) × 3 + 16
本体 < 门槛  →  保持内联
```

即「按最坏情况的搬运量估，仍要求 N=2 净省 16 B」。实测分界：

| 用例 | 本体 | 入/出槽 | 门槛 | 结果 |
|---|---:|---:|---:|---|
| `mul.zig` | 36 B | 4 / 2 | 34 B | 通过（125 → 93 B） |
| `div.zig` | 35 B | 6 / 4 | 46 B | 拦下（共享后持平） |
| `cordic_sin.zig` | 40 B | 12 / 4 | 64 B | 拦下（共享后 +16 B） |

另有硬上限 `MAX_SHARE_SLOTS = 10`：单块参与的槽超过 10 个直接放弃。

## 8. 宽局部量槽回收（同轮修复）

`airLastRead` 返回的是 **AIR 指令编号**，而 `freeDeadScratch(at)` 收到的
`at` 是 **body 下标**——两套尺度直接比较，结果是「该留的被提前回收、该还的
永远不还」。这是宽局部量回收三次回退的根因。

修法：`ScratchRun` 记录 `last`（AIR 指令编号）与 `body`（分配时所在 body 的
标识），只在**同一 body 内**比较；`emitBody` 进出时切换 `cur_body`，退出时
`freeScratchOfBody` 把该 body 创建的 scratch 整段还池。

效果：DSEG 峰值 **74 B → 65 B**（`cordic_sqrt.zig`），`div.zig` /
`cordic_sin.zig` 各 **−13 B** 代码。

### 8.1 顺带修掉的既有 bug

槽回收让 vreg 编号变小、落进 bank0（0x00-0x07），从而暴露：

- `orl rN,#data` / `anl rN,#data` / `xrl rN,#data` **在 8051 上不存在**
  （只有 `orl direct,#data`）。`byteText` 把 0x00-0x07 渲染成 `rN` 是为了
  `mov a,r6` 省 1 B，但这个折叠不能用在立即数形式的逻辑运算上。
  新增 `dirAddrText()`，三处统一改用直址写法 `0x0N`。

### 8.2 pass 顺序调整

`assignRegisters`（M2.13）会把 `dst == lhs` 的热点值搬进 r5/r6/r7，操作数
从 `.vreg` 变成 `.dir`，块就不再是「纯 vreg 直线算术」，factor 判定整块失效。
因此 factor 必须排在 `reuseSlots` 之后、`assignRegisters` **之前**。

## 9. 已知限制与下一步

- 单站点净亏：`generate()` 逐函数产出、文本一旦发出无法回头，无法预知
  「后面还有没有第二个站点」。完整程序口径实测（`bincompare.py` 的 Δ 列）：
  16 位算子 −8 B、32 位算子 −14 B。要做到 N=1 零开销，需把决策推迟到链接期，
  或在编译开始前预扫描全单元 AIR。**本轮评估后放弃**：跨函数预扫描要在 link
  层拦截，而收益上限就是这一个站点的成本（8～14 B），性价比不成立。
  缓解方向见下面第 1 条（让例程内部的槽间搬运归零，能把 −14 B 压到 −2 B）。
- 拥有者函数的槽被其它函数经共享例程临时使用；若「拥有者执行中 → 调用别的
  函数 → 别的函数又用同一共享例程」，活值可能被覆盖。mcs2 的静态参数区
  本来就不支持重入（非尾自递归已编译期拒绝），此处沿用同一约束。
- 同函数内重复模板整组放弃（见 §3.6）。彻底支持需要给共享例程分配专用槽，
  会占 DSEG，与 80 B 上限冲突。
- 按「用编译速度换安全和固件大小很值」的口径，下一批候选：
  1. **多遍优化**：对共享例程本身再跑一遍窥孔与槽复用；
  2. **共享例程专用槽 + 静态内存预算检查**，解除同函数重复与重入限制；
  3. **JUMPTABLE / 函数指针表**：把「同签名、不同算法」的分派也压到一处。
