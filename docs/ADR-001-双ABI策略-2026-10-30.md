# ADR-001：mcs2 双 ABI 策略（内部最优 ABI + SDCC 边界兼容层）

> 状态：**已决策（2026-10-30，用户定调）**
> 适用：mcs2 全部调用相关设计；接手者从这里开始理解 ABI。
> 背景实测：`docs/对照-add函数四方汇编-2026-10-30.md`（四方汇编并排 + ABI 事实表）。

---

## 1. 决策

**SDCC 的 C-ABI 只是「C↔Zig 边界」的兼容层；纯 Zig 内部调用按最优方案实现。**

| | 边界 ABI | 内部 ABI |
|---|---|---|
| 适用范围 | **仅** `export fn`（被 C 调）与 `extern fn`（调 C） | 其余一切 Zig 函数间调用 |
| 语义 | 与 SDCC `--model-small` 产物**逐字节对齐** | 按 mcs2 自己的最优值位置设计，随时可改 |
| 标记方式 | Zig 语言自带：`export` / `extern` 就是边界标记，**不需要额外语法** | 默认 |
| 存在理由 | 与 SDCC 编的 C（如 `usb_cdc_lib`）直接混链 | 尺寸/速度追 Keil 量级，不受 C 约束 |

类比：Rust 的 `"C" ABI` vs 内部 fastcall；Swift 的 C ABI vs ownership ABI。
这是工具链的标准做法，不是妥协。

## 2. 边界 ABI 的真值来源（已实测，勿凭手册）

SDCC 4.6.0 `-mmcs51 --model-small` 对 `add(u8,u8)->u8` 的实测：

- **arg0 → DPL**（0x82）；
- **arg1+ → 静态 `_函数名_PARM_n` 区**（`.area DSEG`，非可重入）——**不是 DPH**；
- 返回值 → DPL；
- `--sdcccall=1` 实测**不改变**第二参数的去处（产物相同）；
- 结论真值的方法论：**每次以 SDCC 实测产物为准**（`sdcc -S` 看汇编），不信手册记忆。

## 3. 当前的账（为什么这个决策是必须的）

同函数四方尺寸：Keil 4B / mcs2 8B / SDCC 9B / 旧后端 18B。
mcs2 的 arg1=DPH 与 SDCC 的 `_PARM_2` 不一致——**不决策就混不了链**。
旧后端的 arg1=栈 又是第三种。三个工具链三种 ABI，谁也不让谁。

## 4. 给接手者的推进规则（按顺序执行）

1. **M1（现在）**：全部函数仍走边界形态（还没有内部调用）；但 arg1+ 必须从
   `DPH` 改为 SDCC 的 `_PARM_n` 静态区（边界 ABI 修正，保证 M3 混链可通）。
2. **M2（控制流+调用落地时）**：
   - 内部 ABI 在 `mcs2/abi.zig` **一处**定义（函数级合同，注释写死理由）；
     首选候选：Keil 风格寄存器传参（arg→R7/R5…，返回 R7），因为它让
     `add` 这类函数到 4B；
   - `export/extern` 函数生成 **ABI 转换序言/尾声**（边界收参→内部位置；
     内部结果→DPL/返回位），转换开销只出现在边界函数上；
   - 内部 ABI 允许演进，每改一次跑全基准（尺寸 + ucsim 行为）。
3. **M3（老示例/混合链）**：验收增加「SDCC 混链」用例——SDCC 编 C 部分 +
   mcs2 编 Zig 部分 + sdld 链接 + ucsim 跑通，即边界 ABI 的最终验收。
4. **任何 ABI 改动**：先改 `mcs2/abi.zig` 注释里的合同，再改代码；
   `add_check.py` 与混链用例是门禁。
5. **尺寸对比口径**：内部函数与 Keil 直接比；边界函数注明「含 ABI 转换开销」，
   与 SDCC 比而不是与 Keil 比。
