## 4. 下一步假设（按性价比排序）

### 假设 1：`relaxJumps` 造新标签时撞号（最可疑）

`mcs51.zig` 的 `relaxJumps()` 在条件跳转超出 ±128 时展开成「反条件跳过 + ljmp」，
新标签由 `max_label += 1` 生成：

```zig
var max_label: u32 = 0;
for (items.items) |item| switch (item) {
    .label => |n| max_label = @max(max_label, n),
    else => {},
};
...
max_label += 1;
const skip = max_label;
```

注意 `max_label` 初值是 **0**，而局部标签 id 形如 `0x80000006`（tempLabel）和
`label_base + inst*2`（blockHead）。这个 `max_label += 1` 出来的 `skip` **没有检查是否已被占用**。
如果函数里存在 `label_base` 较小的块标签（例如 `L45`），而 temp 标签又是 `0x80000006`，
两者混在同一个 `max_label` 里比较是合理的；但如果展开发生在**第二轮**（`expanded` 结构变更后重算），
`max_label` 会重新从 items 里算 —— 需要确认新插入的 `skip` 有没有被计入下一轮的 `max_label`。

**验证方法**：在造 `skip` 前加一句断言/打印，检查 `max_label + 1` 是否已存在于 `label_off`：

```zig
if (label_off.contains(max_label + 1))
    std.debug.print("COLLIDE {d}\n", .{max_label + 1});
```

### 假设 2：`uniquifyLabels` 的调用时机不对

`mcs51.zig:1029` 调 `uniquifyLabels(gpa, &items)`，把重复定义的标签改名成 `0xF000_0000 + seq`。
如果它在 `relaxJumps` **之前**执行，而松弛阶段又插入了新标签，改名就白做了；反过来如果它在
松弛之后执行，输出里就不该有重复定义 —— 现在**有**，说明它没覆盖到（或根本没在这个路径上跑）。

**验证**：在 `uniquifyLabels` 前后各打一次「重复标签个数」，看它在哪一步、有没有生效。

**注意**：即使改名能消掉「多重定义」报错，**控制流仍然是错的**（`jnz` 还指向旧位置）。
所以 `uniquifyLabels` 是止痛片，不是解药 —— 真正的修法是让 `skip` 标签永不撞号。

### 假设 3：`.label` 项被重复 append

`mcs51.zig` 里 emit label 的地方只有 5 处（`854 / 1012 / 1409 / 1427` 和 `uniquify` 的改名）。
`1409`（原样复制）和 `1427`（新 skip）都在 `relaxJumps` 里；`1012` 是 `ret_lbl`。
逐处确认没有在一条路径上 append 两次。

## 9. DeepSeek 第二轮复测（2026-11-02 12:10）：根因已定位到 `reuseWideDst` 的**存储别名**

按 Kimi 的指示加了 `REUSE` 打印（三个调用点），`sqrt32`/`hypot` 一次构建就出结果：

```
REUSE inst=6  lhs=4  uses=0
REUSE inst=17 lhs=15 uses=0
REUSE inst=22 lhs=20 uses=0
REUSE inst=23 lhs=19 uses=0
REUSE inst=26 lhs=25 uses=0
REUSE inst=28 lhs=26 uses=0
REUSE inst=32 lhs=31 uses=0
REUSE inst=38 lhs=37 uses=0
```

**8 处全部 `uses=0`** —— 不是「偶尔漏一个消费者」，而是这套全函数引用模型对
「变量」这种操作数**结构性失效**。

### 为什么会结构性失效

`wideOperand()`（mcs2.zig:993）在「宽度正好相等」时不拷贝，**直接返回原槽**：

```zig
if (self.wideOf(ref)) |w| {
    const base: u8 = @truncate(w & 0xFF);
    const wn: u8 = @truncate(w >> 8);
    if (wn == n) return base;        // ← 别名：这就是变量 res 的 DSEG 槽
    ...
}
```

而 `var res: u32` 的每次**读**都会自己发一条 `load`，所以那条 `load` 指令确实只有本次
这一个消费者 —— `useCountWholeAir` 回答 `uses=0` 是**对的**，但它回答的是「这条 load 的值还有没有人用」，
而 `reuseWideDst` 需要知道的是「**这块存储**还有没有人在用」。两者不是一回事。

于是 `n >= res + bit` 里的加法把 `res+bit` 写进了 `res` 的槽，分支里再算 `res + bit` 就已经是被污染的值 ——
正是 Kimi 在汇编里看到的「第一次加法写回 res，进分支后再算一次」。

### 修复方向（两条，都需要 Kimi 拍板）

**A. 加别名闸门**（我已实现，开关名 `forbid_alias_reuse`，默认 false）：
操作数是存储别名时禁止原地写回。**正确性没问题，但 `sqrt32` 的 DSEG 从 79 B 涨到 110 B → 装不下**。
所以不能直接开。

**B. 区分「结果写回同一变量」与「结果只是临时」**：
`v = v + x` 这种形态把结果写回 `v` 的槽是**对的**，必须保留；
`n >= v + x` 这种形态才是错的。判据：本指令的结果是否**立刻**被 `store` 回同一地址。
建议在 `reuseWideDst` 里按「消费者是不是 store 到同一槽」来放行 alias 复用 —— 这样既有正确性又保住 DSEG。

### 现场状态

## 10. 合同 B 已实现（2026-11-02 12:25）：**语义修好了，只剩 DSEG 装不下**

### 实现（`reuseWideDst` 重写，按 Kimi 的五条判据）

```zig
if (alias) {                       // ① 操作数是存储别名（变量槽）才走严格判据
    next 必须是 .store/.store_safe;      // 1)
    store.rhs 必须就是本条指令;            // 2)
    目标不能是运行期指针;                  // 5)
    refLoc(store.lhs) 必须 == 同一个槽 a;   // 3)
    写回宽度必须 == n;                     // 4)
} else {
    // ② 操作数本身是临时槽（SSA 语义成立）→ 沿用旧判据（定义在本块 + 全函数无人再读）
}
```

`useCountWholeAir()` **不再**为别名操作数放行（只保留给临时槽，那里它是对的）。
store 里的同槽自拷贝也按要求跳过了（`if (dbase + k2 != sbase + k2)`）。

### 还差什么：DSEG 98 B > 80 B

## 11. 临时槽生命周期实验（2026-11-02 12:55，按 Kimi 的三条约束做完）

### 实验 1：只修 `flushTempsKeep` 的保留语义（keep 重新登记）

**结果：11 项回归失败** —— `memrt, sexcmp, bscale, fbchk, csin90/45/180, ccos0, cat90/45, ringdemo`。

原因：有些临时段被 `keep` 之后会**作为结果继续向后传递**（不止一格），
把它们登记进「下一条指令回收」就会提前复用。这正好印证了 Kimi 说的
「需要同时补齐临时槽的生命周期传递，否则会引入新的提前复用」——已实测坐实。

### 实验 2：owner 感知的生命周期（keep ∪ owner 之后还有读者 → 保留）

`temp_owner[]` + `cur_inst`，flush 时判 `useCountWholeAir(owner, cur) > 0`。

- **133 项全绿**（没有回归）
- 但 `sqrt32` 的 DSEG **98 → 115 B（更差）**：临时段活着的时间变长，把池子里的空洞堵住，
  高水位反而上升。

### 实验 3：只读消费者的结果分到临时槽（cmp / 加减法右操作数 / store 的值）

按 Kimi 的「只放行可证明的只读消费」实现（`load` 与未识别消费者一律不放行）。

- 133 项全绿
- DSEG 仍是 115 B，没有进一步下降

**结论：三个实验都做完了，方向正确但不解决 DSEG 问题。**
把临时槽寿命拉长会让空洞被占住，高水位上升；真正的成本来自被判永久占用的 `allocWide` 块。

### 给 Kimi 的建议

`sqrt32` 里 `res + bit` **被算了两次**（一次给 `cmp_gte`、一次给 `sub`），各占 4 B 永久块。
下一步应该是 **CSE（同一基本块内相同表达式复用结果）**，而不是继续调生命周期：
一次 CSE 就能省 4 B，而且对 `n -= res + bit` 这类重复子式是通杀收益。

当前状态：合同 B 保留（语义正确，已用临时 DSEG 基址验证 1000 / 5）；
三个生命周期实验的代码已回退到原样（`temp_owner` / `scratch_results` / `scratchConsumerOk` 保留但默认关闭）。
全量 `check` **133 项全绿**；`csqrt1m` / `chyp` 仍因 DSEG 超限链不上。

## 12. 永久块账目（2026-11-02 13:35）

`account_wide`（默认关）打开后，cordic_sqrt 的永久 `allocWide` 块：

```
sqrt32  5 块 × 4B = 20B   （inst 0/1/3/5/26；last=2/24/33/39/28 → 后三个是循环变量，合理）
hypot   9 块 ≈ 34B        （**inst=4 分到 base12+base16，inst=5 分到 base21+base25** → 同一指令分配两次，白扔 8B）
absU    2 块 ≈  4B
```

**同一 AIR 指令被 lower 两次**（hypot 的 inst 4/5）—— 和最早那个「循环体发两遍、标签重复」同源。
这才是 ≥18B 的主要来源，不是临时槽寿命。

已完成：scratch 按 AIR 最后读取点回收（`airLastRead`/`allocScratch`/`freeDeadScratch`）、
调用实参计入使用者（`instUsesValue` 补 `.call`）。全量 133 绿，DSEG 仍 98。

## 13. 98 → 85 B（2026-11-02 19:10）

### 修掉的重复分配（hypot inst 4/5 各分配两次的真正原因）

`mulWide()` 内部的循环工作副本用的是 **`allocWide`（永久槽）**：

```zig
const t = try self.allocWide(n);      // ← 每次 u32 乘法白占 4 B
const ctr = try self.allocVreg();     // ← 再 1 B
```

`hypot` 有两次 u32 乘法（`ax*ax`、`ay*ay`）→ 每次在结果之外再永久占 4 B，
账目里就表现为「同一条 AIR 指令两次 allocWide」。改成 `allocTempWide` / `allocSlots(1,true)` 后消失。

### scratch 判据改成「所有使用者都只读」

只看下一条会漏「先算两个、再一起用」的形态（hypot 的两次 `absU` 调用正是）。
改成扫描全函数所有使用者，要求每一个都是只读（cmp / 加减法右操作数 / 乘除任一侧 / store 值 / 实参 / 返回值）。

| 步骤 | DSEG |
|---|---:|
| 合同 B 之后 | 98 B |
| `mulWide` 内部改临时槽 | 89 B |
| 只读判据覆盖全部使用者 | **85 B** |
| 把 `int_cast/trunc` 整体算只读 | ✗ 回归 `fbchk`（恒等转换会直接拿操作数那份当结果） |
| 「变宽的 cast 才算只读」 | ✗ `tableidx.zig` 编译失败 |

### 85 B 的分布（按函数）

```
cordic_sqrt32   36 B   （3 个循环变量各 4 B 是必需的 + 表达式结果）
cordic_hypot    23 B
cordic_absU     18 B   ← 小函数但占 18 B，两个 @intCast 的 4 B 块 + 扩位临时
chyp / csqrt1m   4 B + 4 B
```

还差 5 B。剩余候选都要新的判据（`int_cast` 结果作为 scratch、`absU` 的两条返回路径合并），
不是调参数能解决的。

## 14. sqrt32/hypot 通过验收：98 → 74 B（2026-11-02 19:50）

`csqrt1m` / `chyp` 已进 `ORDER`，全量 **135 项全过**，`cordic_sqrt` 的 DSEG **74 B ≤ 80**。

### 三笔改动（都由 SDCC / Keil 的汇编启发）

| 改动 | 省 | 出处 |
|---|---:|---|
| `0 - x` → `negInto`（二补码取负），不再物化常量 0 块 | 代码 ~8 B | SDCC 的 `clr a; subb a,rN` |
| `x < 0` / `x >= 0`（有符号）→ 测最高字节 bit7 | absU 17→15 槽 | SDCC 的 `jnb acc.7` |
| **常量实参直接写进 ABI 位置**，不物化成槽 | **8 槽**（两个 wrapper 归零） | Keil/SDCC 都直接把常量装进参数寄存器 |

另外两笔更早的：`mulWide` 内部工作副本改临时槽（−9 B）、符号扩展不再用中转槽（−1 B）。

### 逐函数

```
cordic_sqrt32   36 B
cordic_hypot    23 B
cordic_absU     15 B
chyp / csqrt1m   0 B + 0 B   ← 常量实参不再占槽
```

### 三方对比（absU，同功能 C 代码）

| | 代码 | 静态 RAM | 符号判定 |
|---|---:|---:|---|
| Keil C51 | 23 B | 0 | `clr c; xrl a,#80h; subb a,#80h; jnc` |
| SDCC 4.6 | ~30 B | 0 | `jnb acc.7` |
| mcs2 | 代码偏大 | 15 B | 现在也是测 bit7 |

静态 RAM 的差距是**结构性**的（两家都把参数放 R6/R7、返回放 R4..R7），
不是优化能抹平的；要追只能改 ABI（参数驻留寄存器）。
